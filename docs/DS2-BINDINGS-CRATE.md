# Scoping the `darksouls2` bindings crate

What the first typed bindings for DARK SOULS II should be, which hand-maintained constants they
retire, and whether the engine's own reflection data can generate them. This builds on
[`DS2-BINDINGS-SURVEY.md`](DS2-BINDINGS-SURVEY.md) (the measurement) and
[`DS2-BINDINGS-PLAN.md`](DS2-BINDINGS-PLAN.md) (module layout, where the crate lives). Those two
are not repeated here; this adds the usage census, the reflection check and the staged plan.

Every fact carries one tag:

- **[source]** read in source code: this repo, or the local `fromsoftware-rs` checkout at
  `/home/banon/projects/fromsoftware-rs` (commit `16d2661`).
- **[binary]** read in `darksoulsii-deobf.bin` or the Ghidra MCP daemon (port 8766,
  `DarkSoulsII.exe`, read-only).
- **[inferred]** a conclusion drawn from the above that no single read establishes.

## Recommendation

Hand-write the field layouts. Generate the class catalogue.

- DLRF registrations carry a class's name, its parent class and its `sizeof`, plus named method
  invokers. They carry no field list. So they can generate size assertions and the inheritance
  chain for every registered class, and they cannot generate a single field offset. **[binary]**,
  section 3.
- The classes this repo reads most (`GameManagerImp`, `SaveLoadSystem`, the `Fe*` scenes and
  groups, `NvNavigationSystem`) have RTTI but are not DLRF-registered. `CharacterCtrl` and
  `PlayerCtrl` are. **[binary]**, section 3.
- First stage: a `crates/darksouls2` skeleton with `GameManagerImp`, `CharacterCtrl` /
  `PlayerCtrl` and the `.flo` layout records, proven by migrating `ds2-intro-skip`. Section 4.

## 1. What the `darksouls3` crate is

Read from the local checkout. **[source]** unless marked.

| part | where | what it does |
| --- | --- | --- |
| crate root | `crates/darksouls3/src/lib.rs` | one module per Dantelion namespace (`dlio`, `dlkr`, `dltx`, `dlut`, `fd4`), plus game modules `sprj`, `app_menu`, `cs`, and `param`, `rva`, `util`, a private `stl` |
| dependencies | `crates/darksouls3/Cargo.toml` | `fromsoftware-shared`, `fromsoftware-shared-stl` with `msvc2012`, `vtable-rs`, `pelite`, `windows`, `bitfield`, `encoding_rs`, `thiserror` |
| struct style | e.g. `sprj/world_chr_man.rs` | `#[repr(C)]` structs with `_unkNN` padding fields named by offset, `/// Source of name: RTTI` notes, `NonNull`/`OwnedPtr` for pointers |
| virtual calls | `dlkr/allocator.rs`, `dlkr/mutex.rs`, `dlio/stream.rs` | `#[vtable_rs::vtable]` traits, unknown slots kept as `unkNN` placeholders so later slots land at the right index |
| layout checks | `app_menu/new_menu_system.rs`, `fd4/basic_hash_string.rs` | `assert_eq!(size, size_of::<T>())` in tests; only a handful of types carry one |
| singletons | `#[shared::singleton("WorldChrMan")]` and six more | resolved by an FD4 singleton scan in `from-singleton`; DS2 has no FD4, so this path does not exist here (survey section 6c) |
| addresses | `rva.rs`, `rva/bundle.rs`, `rva/rva_ww.rs`, `rva/rva_jp.rs` | an `RvaBundle` struct picked by game version, generated by `tools/binary-mapper` from `mapper-profile.toml` |
| address mapper | `tools/binary-mapper/src/main.rs` | `[[patterns]]` entries are byte signatures; `[[vmts]]` entries resolve a vtable by RTTI class name through `fromsoftware_shared::find_rtti_classes` |
| params | `param/generated.rs` | generated by `tools/param-generator` from paramdef XMLs; nothing in it comes from the binary |

Two things transfer that the survey did not call out:

- **The `[[vmts]]` mapper path works on RTTI names**, and DS2 has MSVC RTTI for its classes.
  `scripts/ds2-rtti.py` already does the same walk offline. So vtable addresses for DS2 can be
  generated rather than typed. **[inferred]** from the mapper source plus the RTTI census; the
  mapper itself has not been run against `DarkSoulsII.exe`.
- **DS3's `DLAllocatorVmt` slot positions agree with DS2 where DS2 has been measured.** DS3 puts
  `allocate` at `+0x48`, `allocate_aligned` at `+0x50`, `deallocate` at `+0x68` **[source]**;
  [`DS2-ALLOCATOR.md`](DS2-ALLOCATOR.md) verified the same three slots in DS2 **[binary]**. DS2's
  vtable is longer, so the trait needs trailing slots, not renumbering. This refines the survey's
  "shape differs" verdict for this one class; it does not license copying other DS3 layouts.

## 2. What this repo already hand-maps

`ds2-game-base` maps no game types: it has no dependency on `ds2-rva` and contains the
fault-safe readers (`mem::safe_read_*`, `mem::read_bytes`) and `mem::game_rva` that every
consumer uses to walk the offsets `ds2-rva` holds. **[source]** So the hand-mapping lives in
`ds2-rva`, and the cost of it shows up as reader calls in the consumers.

Two readings of that table, and they point at different first types:

- **By reach**, `GameManagerImp` wins: its singleton RVA (`GAME_MANAGER_IMP`) is named in more
  consumer crates than any other constant, and its child offsets (`GAME_DATA_MANAGER_OFFSET`, save/load, map, character,

- **By volume**, the `.flo` layout records win: `FLO_RECORD_STRIDE`, `FLO_TRANSFORM_SIZE` and

  `ds2-menu-row` and `ds2-item-warn`. These describe `FeLayoutDocument` data loaded in place from
  `.flo` files, not a C++ object, so RTTI and DLRF say nothing about them. **[source]**, **[binary]**
  (no RTTI descriptor for `FeLayoutDocument`).

The player group comes third: `PLAYER_CTRL_OFFSET`, `PLAYER_CTRL_VTABLE`, `CHARACTER_CTRL_VTABLE`
and the `CHARACTER_CTRL_*` offsets are shared by `ds2-build-import`, `ds2-invasion-path` and
`ds2-item-warn`, and it is the one group where the binary can check the struct size (section 3).

## 3. Can DLRF registrations generate layouts?

Checked on one registration end to end, `DLRF::DLRuntimeClassImpl<CharacterCtrl,0>`, then
spot-checked on its parent and its subclass. **[binary]** throughout unless marked.

**The object.** `FUN_140311bf0` builds it in place at `0x1416145f0` and publishes it through the
lazy getter `FUN_140315860` into `[0x1416145d8]`. The base constructor `FUN_14083efd0` writes:

| offset | contents |
| --- | --- |
| `+0x00` | vtable (`DLRF::DLRuntimeClass`, then the `Impl` vtable at `0x1410df588`) |
| `+0x08` | parent runtime class, zero until registration |
| `+0x10` | zeroed; purpose not identified |
| `+0x18`..`+0x28` | a begin/end/capacity container of method invokers |
| `+0x30` | the DLKR allocator the container uses |
| `+0x38` | `char*` class name, written by the static initialiser |
| `+0x40` | `wchar_t*` class name, written by the static initialiser |

**The static initialisers.** Two small functions with no Ghidra function around them:

- `0x1410745c0` stores `"CharacterCtrl"` (`0x1410df548`) at `+0x38` and `u"CharacterCtrl"`
  (`0x1410df558`) at `+0x40`, then tail-calls `FUN_14083f070`, which panics with
  `DLRuntimeClass.cpp` on null and inserts the class into two global sorted indexes: one keyed
  by name (root at `[0x141668080]`), one keyed by the type-token slots below (root at
  `[0x141668090]`).
- `0x141074590` fetches the parent class through `FUN_1403161c0` and tail-calls
  `FUN_14083f8f0`, which walks the chain to reject a cycle and stores the parent at `+0x08`.
  `FUN_140311490` walks that same `+0x08` chain to answer "is this object a `CharacterCtrl`" --
  that is DLRF's `dynamic_cast`.

**The vtable**, `0x1410df588`, slot by slot (the next qword is the following class's data):

| slot | target | behaviour |
| --- | --- | --- |
| 0 | `FUN_140311a10` | scalar deleting destructor |
| 1 | `FUN_140312a90` | returns `+0x38` (name) |
| 2 | `FUN_140312cd0` | returns `+0x40` (wide name) |
| 3 to 6 | `0x140312cc0`, `0x1403126e0`, `0x140312af0`, `0x1403126d0` | each returns the address of a distinct static byte (`0x1416145e1`..`0x1416145e4`): identity tokens, the keys of the second index |
| 7 | `FUN_1403144e0` | returns `0` |
| 8 | `0x140311cb0` | a thunk Ghidra attributes to an EzState function; likely a folded body, not identified |
| 9 | `FUN_140312b60` | returns `0x480` |
| 10, 11 | `FUN_14083f870`, `FUN_14083f7c0` | register a method invoker into `+0x18`; panic text names `DLMethodResolver.inl` |

**Slot 9 is `sizeof`.** The same slot on one inheritance chain:

| class | `Impl` vtable | slot 9 returns |
| --- | --- | ---: |
| `CharacterCtrlBase` | `0x1410df878` | `0x58` |
| `CharacterCtrl` | `0x1410df588` | `0x480` |
| `PlayerCtrl` | `0x1410e4e58` | `0x4a0` |

The values grow along the chain, and the `CHARACTER_CTRL_*_OFFSET` constants and
`PLAYER_CTRL_CHR_ASM_CTRL_OFFSET` in `ds2-rva` all sit below the matching size. **[inferred]** that slot 9 is the instance size; nothing here
decompiled an allocation of `0x480` next to a `CharacterCtrl` constructor.

**No field metadata.** The DLRF template families in the image are `DLRuntimeClassImpl`,
`DLConcreteMethodInvoker` and `DLConcreteConstructor`, plus the core `DLRuntimeClass`,
`DLAbstractInvokeContext`, `DLMethodInvokeContext` and `DLRuntimeConstructionContext`. None is a
property or field descriptor (`grep -ao` for `Property|Field|Member|Attribute` under `DLRF`
returns nothing). The registration carries no instance pointer either, so it does not answer
singleton discovery -- that half of the plan's open DLRF question is closed.

| DLRF template (RTTI name prefix) | occurrences in `darksoulsii-deobf.bin` |
| --- | ---: |
| `.?AV?$DLRuntimeClassImpl@` | 587 |
| `.?AV?$DLConcreteMethodInvoker@` | 153 |
| `.?AV?$DLConcreteConstructor@` | 78 |

**Coverage of the types this repo uses.** Presence of `DLRuntimeClassImpl@V<name>@@` and of
`.?AV<name>@@` in the image:

| class | RTTI | DLRF-registered |
| --- | --- | --- |
| `GameManagerImp` | yes | no |
| `GameDataManager` | yes | no |
| `SaveLoadSystem` | yes | no |
| `CharacterCtrl` | yes | yes |
| `PlayerCtrl` | yes | yes |
| `NvNavigationSystem` | yes | no |
| `SfxEffectData` | yes | no |
| `FeSubStateTitleLogo`, `FeGroupInGameTopSelect` | yes | no |
| `PlayerParam`, `NvNaviGraph`, `MapManager`, `FeLayoutDocument` | no | no |

Of the registrations with a plain class name, the `Map*` family is the largest; the others
are resource objects (`Sfx*ResourceObject`, `ParamFileResourceObject`), `GameEntity*`
interfaces, the character controllers and the `FeObject*` buttons.

**Verdict.** Generated: a DLRF catalogue (name, parent, `sizeof`) for the registered classes,
used as size assertions and `Subclass` relations, and vtable RVAs by RTTI name. Hand-written:
every field. **[inferred]** from the above.

## 4. Staged plan

Where the crate lives, its module layout and why it has no `rva`, `fd4` or `cs` module are settled
in [`DS2-BINDINGS-PLAN.md`](DS2-BINDINGS-PLAN.md): `crates/darksouls2` in this repo first,
addresses stay in `ds2-rva`. One constraint to add: `darksouls2` depends on `ds2-rva` and must not
re-export it, so that `ds2-game-base`'s `game-types` facade can re-export `darksouls2` without
handing its own code a path to an address.

### Stage 1 -- skeleton, three types, one migrated crate

Contents:

- `crates/darksouls2` with `lib.rs`, `dl/kr.rs` (the allocator trait from
  `DS2-ALLOCATOR.md`) and nothing else from the Dantelion layer.
- `game/game_manager.rs`: `GameManagerImp` as `#[repr(C)]` with the child pointers `ds2-rva`
  already knows (`GAME_DATA_MANAGER_OFFSET`, `GAME_MANAGER_SCREEN_FADE_OFFSET` and the rest of the
  `GAME_MANAGER_*` offsets) as typed, opaque `Option<NonNull<_>>` fields, and a
  `GameManagerImp::instance()` that reads `ds2_rva::GAME_MANAGER_IMP` through
  `ds2_game_base::mem`.
- `game/chr.rs`: `CharacterCtrlBase`, `CharacterCtrl`, `PlayerCtrl` with the known offsets and
  `size_of` assertions of `0x58`, `0x480`, `0x4a0` from the DLRF slot.
- `fe/flo.rs`: the `.flo` definition, record and transform structs behind `FLO_DEFINITION_STRIDE`,
  `FLO_RECORD_STRIDE` and `FLO_TRANSFORM_SIZE`.
- Proof: `ds2-intro-skip` reads `GameManagerImp` and its screen fade through the new types and
  drops its `GAME_MANAGER_*` / `SCREEN_FADE_*` imports.

Acceptance:

- `bash scripts/check.sh` passes with the new crate in the workspace.
- Every struct field's offset matches the `ds2-rva` constant it replaces, asserted with
  `core::mem::offset_of!` in the crate's tests, so the two cannot drift silently.
- `ds2-intro-skip` launched through `scripts/ds2-run.py` shows the same intro-skip log lines as
  the pre-migration commit.
- The `ds2-rva` constants the migration made unused are deleted or marked as owned by the struct,
  not left as a second source of truth.

### Stage 2 -- the DLRF catalogue, generated

Contents: a `scripts/` walker over `darksoulsii-deobf.bin` that finds every
`DLRuntimeClassImpl<...>` vtable by RTTI (as `scripts/ds2-rtti.py` does), reads slot 9, reads the
parent from the static initialiser, and emits `darksouls2/src/dlrf_generated.rs` with one size
constant and parent link per class.

Acceptance: the generated rows for `CharacterCtrlBase`, `CharacterCtrl` and `PlayerCtrl` equal
the table in section 3; the walker reports how many registrations it could not resolve rather
than dropping them; stage 1's hand-written size assertions switch to the generated constants.

### Stage 3 -- migrate by reach

Contents: move the remaining `GAME_MANAGER_IMP` consumers (`ds2-continue`, `ds2-boot-timeline`,
`ds2-offline`, `ds2-voice-chat`, `ds2-save-file`, `ds2-invasion-path`, `ds2-build-import`,
`ds2-item-warn`, `ds2-menu-row`) onto `GameManagerImp`, and the `.flo` consumers
(`ds2-menu-row`, `ds2-item-warn`) onto `fe::flo`.

Acceptance per crate: check gate green, one `scripts/ds2-run.py` run whose log matches the
feature's existing evidence lines, and the crate's `GAME_MANAGER_*` / `FLO_*` imports gone.

### Stage 4 -- the next areas

`SaveLoadSystem` (second by reach in section 2a), then navigation and SFX (a single consumer
each, so lowest priority by this measure), then `param` from the paramdef slice already drafted on the
`fromsoftware-rs` fork. Each gets the same acceptance as stage 3.

### Stage 5 -- upstream

Move `crates/darksouls2` into `fromsoftware-rs` once the conditions in
`DS2-BINDINGS-PLAN.md` hold (layouts proven by runtime, the `shared::singleton` and
`shared::arxan` gaps answered), with vtable RVAs produced by `binary-mapper`'s `[[vmts]]` path.

Acceptance: `binary-mapper` generates the DS2 `RvaBundle` from `DarkSoulsII.exe` and its vtable
entries equal `ds2-rva`'s `*_VTABLE` constants.

## Reproduce

```
python3 scripts/ds2-rva-census.py
python3 scripts/ds2-rva-census.py --area GameManagerImp
python3 scripts/ds2-rtti.py '?$DLRuntimeClassImpl@VCharacterCtrl@@$0A@@DLRF'
xxd -e -g8 -s 0x10df588 -l 0x60 darksoulsii-deobf.bin
objdump -D -b binary -m i386:x86-64 -M intel --adjust-vma=0x140000000 \
  --start-address=0x141074590 --stop-address=0x1410745f8 darksoulsii-deobf.bin
```

Decompiles, through the Ghidra MCP daemon on port 8766: `0x140311bf0`, `0x14083efd0`,
`0x14083f070`, `0x14083f8f0`, `0x140311490`, `0x140312b60`, `0x140315f10`. `PlayerCtrl`'s slot 9
(`0x14037f3a0`) is not inside a Ghidra function; read it with `objdump` as above.
